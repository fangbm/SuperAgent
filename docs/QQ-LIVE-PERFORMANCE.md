# QQ 实时查询的本地性能记录

日期：2026-11-05。测量对象为 PR #14 的查询实现 `8d6c657f9e7d932814bc31a3aeda684daf490a32`，本轮只增加基准工具和证据，未修改业务查询。原始结果见 [JSON 记录](evidence/qq-live-perf-2026-11-05.json)。

## 当前结论

这项仍列为扩展性风险。初始快照已有明显延迟，数万条数据的首次待办查询超出本次预算；功能分页回归不能作为性能验收结果。尚未定义产品延迟 SLA，本记录不把耗时转换成正确性 Bug，也不宣称完成上线性能验收。

真实 QQ 的群原生格式、常驻菜单、原生 `/` 面板和被动回复时限均未执行本轮验收。全量消息权限、受控 API 测试和本地性能数据分别记录，不扩大真实平台验证范围。

## 负载与环境

- Windows x64，Node 24.22.2（同一二进制的 SQLite 3.53.4），Ryzen 9 8945HX、32 逻辑处理器、31 GiB 可见内存；环境原值及源码/构建产物哈希在 JSON 中。
- 每档新建文件 SQLite，沿用现有 WAL/FULL 设置；只使用进程自有临时目录，结束或超时后关闭/终止子进程并核对目录范围再清理。没有打开历史业务库。
- 合成数据直写 fixture：每工作项 10 条已分析消息、10 个 FeedbackItem/primary 关联；Bug/建议各一半，混合未处理和终结状态。5% 工作项包含截止后的新反馈，另加已分析消息数 1% 的待分析原始消息。
- 已填充相关归档、对象/路由、Admission、Batch/Job、提取及工作项关联表，检查计数和外键；`model_calls`、`external_operations` 均为 0。未运行真实 Ingress/M3 接入、LLM、QQ 或网络投递，不用于证明这些路径的吞吐量。
- 四种模式按 pending → recent → all-bugs → all-suggestions 顺序运行，目标每模式 3 次。同库保留本轮查询快照；不清系统缓存、不模拟并发、不强制 GC，包含 Store 调用计数开销。
- 每次快照查询预算 30 秒，每档总预算 180 秒。父进程独立计时，超时终止合成负载子进程并保留种子数据规模、阶段和查询计划。超时只记录未完成，不能当成 30 秒完成耗时。

## 测量结果

| 已分析反馈 / 工作项 | 额外待分析消息 | 待办初始快照 | 新增初始快照 | 全部 Bug | 全部建议 |
| --- | --- | --- | --- | --- | --- |
| 10,000 / 1,000 | 100 | 8.981 秒 | 11.170 秒 | 5.567 秒 | 5.560 秒 |
| 50,000 / 5,000 | 500 | 首次查询超出 30 秒预算并中断 | 未执行 | 未执行 | 未执行 |
| 100,000 / 10,000 | 1,000 | 首次查询超出 30 秒预算并中断 | 未执行 | 未执行 | 未执行 |

首行是 3 次观测的中位数，完整样本与最大值保留在 JSON；不据 3 次样本推断总体 p95。后两档的时限中断分别在查询阶段约 30.023/30.018 秒被观测到，含进程调度与终止开销，不是成功查询结果。

第一档建成快照后，每种模式做 90 次首页/中间/末尾页查询，中位耗时为 0.022–0.027 毫秒，使用 ordinal 主键索引。该指标不包含创建快照、Markdown 组装或 C2C 网络耗时，不能用它代表用户首次查询延迟。50,000/100,000 档没有建成快照，不报告它们的翻页耗时。

同步快照期间零延迟定时器的观测延迟与快照耗时相近（例如 recent 中位约 11.170 秒），说明同一 Node 线程在这段时间无法及时处理该定时器。本轮未测量并发 M1/M3/M5、Gateway 心跳或真实被动回复期限的影响。

## 查询成本观察与后续工作

第一档 recent 只有 50 个工作项含新反馈，仍执行 1,000 次关联反馈查询；pending 对 300 个符合状态的工作项执行 300 次。统计的是 `SqliteStore.get/all/run/exec` 调用，不包含其内部 BEGIN/COMMIT。

本机记录的关联反馈 EXPLAIN 显示：首次接收时间的相关子查询只记录 `qq_object_received (source_id=?)` 的索引前缀，同时使用临时分组/排序 B-Tree。应进一步验证完整对象谓词的索引利用及批量聚合方案；本轮没有对各 SQL 单独计时，不量化单一原因的贡献。

后续优化应保留首次接收时间、primary 去重、项目权限和稳定分页语义，优先检查对象定位/索引谓词、批量统计以及避免 recent 逐项遍历全部历史。快照复用、构建预算和同步阻塞也需要单独评估；这些优化未在本轮实施。

这仍是有限合成负载：单项目/单 Source、每项固定 10 条反馈，没有覆盖热点大工作项、历史编辑/纠错分布、多来源、多项目、长期积压和并发用户，不能推断所有部署的性能。

## 复现

```powershell
pnpm build
pnpm bench:qq-live --samples 3 --query-timeout-ms 30000 --output .artifacts/qq-live-perf-new.json
# 小规模检查工具；输出文件需尚不存在
pnpm bench:qq-live --scales 20:200 --samples 1 --output .artifacts/qq-live-perf-smoke-new.json
```

脚本仅接收合成规模，不接收现有数据库路径；每档最多 20,000 个工作项、200,000 条反馈，每项最多 30 条。JSON 中每档 `status` 必须单独检查；工具返回成功表示证据收集完成，`query_timeout`/`case_timeout` 档不算性能通过。当前性能基准不加入普通 `pnpm check`，避免把高负载基准放进每次功能 CI。
